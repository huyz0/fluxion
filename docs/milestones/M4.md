## Goal

`fluxion validate` and `fluxion render` work from Node on Windows, macOS and Linux. Given
`examples/r0-static.flux.json`, the CLI writes one static HTML file. It shows each screen at
its logical size and background, with rectangles and straight connectors styled through a
minimal token theme. That HTML comes from the same React `<ScreenView>` the player and editor
will use. This milestone closes increment R0.

## Requirements

FR-CLI-001, FR-SCR-001 (render), FR-THM-001 (part: minimal token model + light theme; full
model in M9), FR-EXT-001 (part: `elementViews` render registry), FR-DOC-005 (part:
unknown-kind placeholder), FR-SHP-001 (render of `core:rect`), FR-CON-001 (render of straight
bound connector).

## Decide before coding

- ADR-0015: static render path. Covers `react-dom/server` rendering of `<ScreenView>` in Node vs
  a hand-written SVG serializer, how CSS Modules content CSS is extracted and inlined, and
  what the Node `TextMeasurer` does in R0 (fixed metrics; fontkit arrives with text in M7).
- ADR-0010 (styling isolation) is the reference: content CSS uses `fx-` + `@layer fx.content`,
  never Tailwind.

## Scope / Non-scope

- In: minimal `theme` package (color roles, fonts, spacing), resolved-style computed in core,
  `<ScreenView>` layers (background, content, editOverlay slot), `mode-policy.ts`, the element
  view registry, rect shape view, straight connector view, placeholder view, SSR to static HTML,
  `fluxion` CLI with `validate` and `render`, SVG goldens, the first visual baseline, the R0 demo
  and exit checklist.
- Out: other shapes, anchors and routers (M5), text editing (M7), the interactive player (M11),
  `.flux` containers (M10), theme switching (M9).

## Handed off from M3 (final review)

Each item becomes a row of M4's backlog when M4 is planned; F2, F4, F5 and F6 together form the
first row (core pre-release hardening, before render consumes core).

- **Undo budget keeps being measured:** the NFR-PERF-006 benches run only in m3-complete. Move the bench leg into milestone-checks.mjs and use it from m4-complete on (or run `pnpm bench` in the nightly perf job now), and reword the ADR-0014 M3.23 amendment to what actually runs (M3 final F1).
- **Command callers cannot forge history origins:** `CommandContext.options` accepts `origin: 'undo' | 'redo'`, which skips hooks and history; restrict the type and refuse it in `executeCommand` with a diagnostic (M3 final F2).
- **One wired core bootstrap:** `createStore(file)` has no hooks and `createCoreRegistries()` has no built-ins; provide one call that registers CORE_HOOKS and CORE_COMMANDS and creates the store with the hooks, used by render and the tests (M3 final F3).
- **Core determinism (NFR-REL-005):** a test runs the same command sequence twice and compares diffs (entry order included), history and document (M3 final F4).
- **Argument errors have one code:** unknown or wrong-typed ids return COMMAND_ARGS (not TX_INVALID); applyFork misuse and a failed keyBetween carry a diagnostic (M3 final F5).
- **Mutation testing with tzap (user decision 2026-09-28):** ADR that tzap (`@huyz0/tzap`, Apache-2.0) replaces StrykerJS in ADR-0008 and tech-stack; dev dependency, `pnpm mutate`, diff-scoped run in the nightly job, floors in `.harness/baselines/mutation.json`. A trial over M3's changed lines (`tzap run --from a34a9c3`, via npx) scored 84.0%: 1 222 valid mutants, 187 survived and 9 had no coverage. Of the survivors, 78 are message strings; the others are logic in builtin-commands, hooks, indexes (sorted members, counts), store, transaction and history, plus a few equivalent ones (the record-map copy count). Triage them before render consumes core: kill each one with a test, or argue it as equivalent.
- **Write-path test not lexical-only:** catch `transact.call/apply/bind` and `ctx`-named helpers outside commands, with mutants (M3 final F6).

## Learned

- cp1: a gate leg that counts output (screens, scripts) cannot tell styled from unstyled; legs for a rendered artefact must check the content that makes it right (inlined CSS, defined vars, shapes present).
- cp1: gate latency is a plan item: rows that add browser, SSR and CLI suites need a ladder budget row before them, not after the budget trips.
- final: a platform break can sit under many commits when the loop never reads main's CI after a push; check the last run before each task, and read CI as soon as a row adds a cross-package dependency.
- final: rows grew 1.9x the plan, a third of it ladder latency and flakes; plan budget and flake rows up front for milestones that add suites.
