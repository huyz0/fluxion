# Standards

How Fluxion is built. Each standard opens with a `> Read when:` line; load a standard only when
that line matches what you are about to do (skills name the ones they need). Numbered rules name
the gate that enforces them, or say `no gate — judgement`.

What to build is in [`../requirements`](../requirements); how the system is shaped is in
[`../architecture`](../architecture); delivery order is in [`../milestones`](../milestones).

The table below is generated by `node scripts/harness/build-index.mjs` from each file's
`Read when` line; do not edit it by hand (`build-index.mjs --check` fails on drift).

## Families

| Family | Covers |
|---|---|
| Process | how work flows from requirement to reviewed commit |
| Quality | what evidence a change must carry (tests, perf, security) |
| Delivery | how changes reach `main`, users, and readers (CI, releases, docs) |
| Code | how source is written, structured, and exposed |
| Design | how the editor and player look, read, and behave for people |

## Changing a standard

A standard is changed like code: its own backlog row, reviewed per [review.md](review.md), and
`build-index.mjs` re-run in the same commit. Loosening a rule that a gate enforces is a threshold
change ([git.md](git.md) trailers) and needs an ADR.
